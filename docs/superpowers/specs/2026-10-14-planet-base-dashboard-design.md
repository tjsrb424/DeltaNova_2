# Delta Nova 행성 기지·조선·대시보드 상세 설계

2026-10-14. 상태: 사용자 진행 요청으로 서면 설계 승인. [파일별 구현계획](../plans/2026-10-14-planet-base-dashboard.md) 검토와 실행 방식 선택 대기, 제품 코드 미구현.

사용자는 다음 개발 순서를 확인한 뒤 진행을 요청했다. 이번 범위는 첫 번째 단계인 행성별 기지 운영·실제 조선·v0.5 대시보드다. 생산한 자원으로 시설과 함선을 늘리고 그 결과를 같은 화면에서 확인하는 경험을 만든다. 성계 비행·NPC 공격 접근·첫 식민지 개척·수송은 다음 단계다.

## 기준과 현재 증거

- [제국 운영 방향 v0.2](../../design/DELTA_NOVA_EMPIRE_DIRECTION_V0.2.md), [식민지 방향](../../design/DELTA_NOVA_COLONIES_V0.1.md), [대시보드 v0.5 화면 규칙](../../art/PLANET_DASHBOARD_UI_V0.5_REVIEW.md)을 따른다.
- `src/base/types.ts`는 참가자별 단일 기지에 합금·보급, 시설 두 종류, 정비량, 개인 작전을 저장한다. 행성·건설 시간·조선·동적 보유 함선은 없다.
- `src/game/fleet.ts`와 저장 검증은 고정 `ROSTER`를 사용한다. 건조한 함선을 화면에 더하는 것만으로 실제 작전에 사용할 수 없다.
- `server/store.ts`는 SQLite의 `world`와 `receipts`를 한 트랜잭션에서 갱신한다. v1 공동 저장과 영수증을 v2 기지 저장으로 이전한다.
- 개인 기지 명령도 현재 공동 작전의 revision과 operationId를 검사한다. 새 행성 명령은 공동 작전 교체와 분리한다.
- 현재 기본 화면은 지휘실이다. v0.5 선정 PNG는 정적인 참고 이미지이며 게임 화면에 적용되지 않았다.
- 변경 전 헤드리스 검증: `npm test` 9개 파일/96개 테스트 통과, `npm run build` 통과. SQLite 실험 API 경고는 기존 환경에서도 발생한다.

## 접근 선택

1. **같은 SQLite에 행성 자산 장부를 도입하고 기존 작전을 연결한다 — 선택.** 자원과 함선의 소유권을 하나로 유지하고 기존 중복 명령 방지와 원자적 저장을 재사용한다. 개인 제국 명령의 버전 검사는 공동 작전과 분리한다. 저장 이전과 서버 작전의 동적 함선 지원이 필요하다.
2. 별도 제국 저장으로 시작하고 기존 기지·공동 작전을 독립 체험으로 남긴다. 구현 경계는 단순하지만 같은 참가자가 서로 다른 자원과 함대를 가지게 된다. 기존 개인/공동 작전이 같은 자산을 사용한다는 제품 계약과 어긋나므로 선택하지 않는다.
3. 대시보드와 건조 버튼만 먼저 추가한다. 화면은 빠르게 바뀌지만 행성 소유권·실제 재고·작업 시각을 뒤늦게 다시 설계해야 한다. 이번 완료 기준을 만족하지 못한다.

## 이번에 제공하는 플레이

개발 참가자로 연결 → 본성 자원 확인 → 생산 시설/조선소 선택 → 비용·시간 확인 → 시설 증설 또는 함선 건조 → 진행 목록에서 완료 확인 → 늘어난 함대로 기존 개인/공동 작전 → 귀환·정비 → 재투자.

처음에는 본성 **노바 프라임 한 개**를 실제 소유한다. 다른 식민지나 이동 작업을 가짜로 표시하지 않는다. 행성 모델과 UI는 복수 소유 행성으로 확장 가능하고, 두 행성을 가진 테스트 픽스처로 현지 자산 경계를 검증한다. 이번 제품에는 개척 명령이나 새 행성 지급 기능이 없다.

## 자산과 데이터 경계

`src/empire/`에 행성 규칙·콘텐츠·검증·이전·서버 API 타입을 둔다. 경제 규칙은 UI·SQLite·브라우저 시각에 의존하지 않는 순수 함수다.

- `EmpireState`: 개인 revision, 본성 ID, 소유 행성 목록, 제국 공통 기술, 제국 연구 작업, 서버 개인 작전과 출격 원점, 새 함선 식별자 생성 상태.
- `PlanetState`: ID·이름·성격, 합금/결정/연료, 저장 상한, 시설 수준, 생산 기준 시각과 소수 분 보정량, 건설 작업 한 개, 조선 작업 한 개, 방어 포대 수량, 실제 보유 함선.
- `ShipInstance`: 고유 ID, 함종 ID, 주둔 행성 ID, 정비 필요량, 도킹/출격 상태. 같은 ID는 한 장부에 한 번만 존재한다.
- `TimedJob`: 고유 ID, 종류, 비용을 낸 행성 ID, 대상/수량, 시작·완료 시각, 시작 때 확정한 비용. 생산/비용 공식 변경에 따라 진행 중 작업의 계약이 바뀌지 않게 한다.
- `EmpireResearch`: 산업·추진·정보·방어 기술의 수준. 기존 HP/화물 모듈 해금·활성 상태와 연구 데이터는 이전 후에도 보존한다.

자원·시설·방어·함대는 행성 현지 자산이다. 연구 수준은 제국 공통이지만 연구 비용은 명시한 소유 행성 한 곳에서 지불한다. 행성 선택은 UI 상태이며 명령의 행성 ID를 자동으로 바꾸지 않는다.

새 서버 저장은 schemaVersion 3 / rulesVersion `planet-base-v3`로 구분한다. 공동 역할·보고서·공헌·보상 기록은 보존하고, 참가자의 기존 `base` 자산을 `empire`의 본성으로 이전한다. 자원·정비·재고의 정본을 `base`와 `empire`에 중복 저장하지 않는다. 필요한 기존 화면용 구조는 명시적인 읽기 어댑터로 만든다.

## 경제 초깃값과 시제품 수치

아래 값은 이번 첫 구현의 검증 가능한 기준이며 최종 밸런스가 아니다. 시안의 K/M 단위 비용과 대기 시간을 그대로 사용하지 않는다.

| 항목 | 새 참가자의 초기 상태 / 효과 |
|---|---|
| 자원 | 합금120, 결정80, 연료80 |
| 합금 광산 | 레벨1, 분당6×레벨, 저장300+100×(레벨−1) |
| 결정 채굴소 | 레벨1, 분당4×레벨, 저장200+100×(레벨−1) |
| 연료 합성소 | 레벨1, 분당4×레벨, 저장150+50×(레벨−1) |
| 발전소 | 레벨1, 공급 전력60×레벨 |
| 생산 전력 수요 | 합금6×레벨, 결정4×레벨, 연료6×레벨 |
| 조선소 / 연구소 | 각 레벨1, 상시 전력 수요8 / 6 |
| 방어 | 포대0기, 완성 포대당 상시 전력 수요2 |
| 시설 공간 | 최대30, 완성 시설 레벨 합계와 진행 중 증설1칸을 사용량으로 계산 |
| 기존 보유 함대 | 현재 8함종/9척을 유지, 이후 건조로 실제 재고 증가 |

전력 부족 때 생산률은 `floor(기본 생산률 × min(1, 공급/수요))`로 낮춘다. 새 건설·건조·연구는 시작 시 전력 부족이면 거절하고 부족량을 보여준다. 이미 시작한 작업은 확정한 완료 시각을 지킨다. 완성된 증설/포대로 전력이 부족해지면 생산률 저하와 발전소 증설을 안내한다. 전력을 저장 자원처럼 차감하지 않는다.

기존 생산의 완전한 분 단위·최대8시간·저장 포화 폐기 정책을 유지한다. 작업 완료로 생산률이 바뀌면 해당 완료 시각 이전에는 옛 생산률, 이후에는 새 생산률을 적용한다. 반복 조회나 여러 작업 완료로 8시간 한도가 세그먼트마다 다시 생기지 않는다. 발전/기술 변화에도 미완성 분의 옛 생산을 소급해서 늘리지 않는다.

### 건설과 취소

행성별 건설 작업은 한 개다. 완료될 다음 레벨의 공간을 시작 때 예약한다. 초기 최대 시설 레벨은5다.

- 생산 시설/발전소 증설: 현재 레벨 L 기준 합금40L·결정10L·연료10L, 시간60L초.
- 조선소/연구소 증설: 합금60L·결정30L·연료10L, 시간90L초.
- 포대 건설: 합금50·결정20·연료5, 60초, 별도 함선이 아닌 현지 방어 재고를1기 늘린다. 건설 작업을 사용하고 시설 공간1칸을 사용한다.
- 시설 최대 수준·예약 공간·비용·필요 전력·진행 중 작업을 서버가 검사한다. 새 시설/포대 완성에 따른 전력 예측도 시작 전 표시한다.
- 완료 전 취소는 시작 비용의 자원별 `floor(비용×0.8)`를 원 지불 행성에 반환하고 공간 예약을 해제한다. 저장 상한을 넘는 반환분은 버리지 않고 취소 명령을 거절하며 부족 공간을 알린다.
- 완료 시각에 도달한 작업은 먼저 완료 처리하므로 취소/환불할 수 없다. 같은 작업 취소·완료를 중복 적용하지 않는다.

### 조선과 실제 재고

행성별 조선 작업은 한 개이며, 시작 수량1..20을 허용한다. 총비용과 시간은 아래 단가에 수량을 곱한다. 조선소 레벨은 요구조건이며 이번에는 작업 시간을 줄이지 않는다.

| 기존 함종 | 합금 | 결정 | 연료 | 척당 초 | 필요 조건 |
|---|---:|---:|---:|---:|---|
| 정찰함 위스프 | 20 | 10 | 5 | 20 | 조선소1 |
| 회수함 아틀라스 | 30 | 10 | 5 | 30 | 조선소1 |
| 타격함 케스트럴 | 40 | 20 | 10 | 40 | 조선소1 |
| 정비함 멘더 | 40 | 30 | 10 | 45 | 조선소1·산업1 |
| 교란함 베일 | 40 | 40 | 15 | 50 | 조선소1·정보1 |
| 호위함 바스티온 | 70 | 30 | 15 | 60 | 조선소2·방어1 |
| 공성함 랜서 | 80 | 30 | 20 | 70 | 조선소2·방어1 |
| 항모 아크 | 120 | 80 | 30 | 100 | 조선소3·산업2 |

기존에 지급된 함선은 새 건조 조건 때문에 사용 불가가 되지 않는다. 신규 함종은 이번에 추가하지 않는다. 완료 때 고유 ID의 건강한 함선을 신청 수량만큼 해당 행성에 한 번 지급한다. 예정 수량은 실제 가용 함선으로 포함하지 않는다. 조선 취소도 건설과 같은80% 반환/상한 검사 규칙을 사용한다.

### 제국 공통 연구

제국 연구 작업 한 개를 사용한다. 새 연구는 기존 작전 최고 성과 데이터를 소모하지 않고 비용 지불 행성의 생산 자원을 쓴다. 기술 초기 수준0, 이번 최대 수준3이다.

- 다음 수준 N 연구 비용: 합금40N·결정30N·연료10N, 시간90N초, 연구소 수준≥N.
- 산업: 수준당 세 자원의 기본 생산률에1을 더하고 멘더/항모 건조 조건을 해금한다. 모든 소유 행성에 같은 완료 시각으로 반영한다.
- 추진: 기술 수준을 저장하고 다음 성계 비행 단계의 선행 조건으로 준비한다. 이번 화면에 실제 비행 속도 보너스가 적용됐다고 표시하지 않는다.
- 정보: 베일 건조 조건을 해금한다. 정찰 보고서의 정보 해상도 효과는 다음 단계다.
- 방어: 바스티온/랜서 건조 조건을 해금한다. 이번에는 포대/함선의 전투 수치를 임의로 바꾸지 않는다.
- 시작/취소는 비용 출처, 시간, 즉시 적용 효과와 후속 사용처를 표시한다. 취소 정책은 건설과 같다.

## 기존 개인·공동 작전과 연결

브라우저 편성 연습은 기존 `ROSTER`, 무료 연구, 로컬 저장과6척/지휘12 규칙을 그대로 사용한다. 서버의 제국 재고를 브라우저 연습에 자동 복사하지 않는다.

서버 작전은 권한 있는 현지 `ShipInstance` 목록으로 편성·정비·출격 검증을 한다. 기존 개인/공동 작전의6척/지휘12는 기존 임무에 한정한 전투 규칙이다. 제국 전체 보유 함선 수의 상한으로 사용하지 않는다. 성계 단계의 함대 규모 규칙은 다음 설계에서 정한다.

- 개인 출격은 출발 행성 ID와 선택 함선 ID를 함께 명령에 고정한다. 가용성·정비 상태·연료를 검증하고 함선 위치를 출격으로 바꾼다. 개인 작전 하나라는 기존 진행 제한을 유지한다.
- 기존 보급 비용은 연료 비용으로 이름을 바꾸되 지휘 합계와 지원+2라는 계산은 이 임무 단계에서 유지한다. 새 거리/왕복 연료 공식처럼 설명하지 않는다.
- 개인 귀환은 원 출발 행성에 함선·정비량·합금 화물을 정산한다. 사용자가 다른 행성을 보고 있어도 귀환지가 바뀌지 않는다.
- 공동 역할은 기존 즉시 전투/귀환 성격을 유지한다. 명령 하나에서 현지 연료 지출·전투·정비량·공헌·보상을 원자적으로 처리한다.
- 서버 전투에는 고정 ROSTER 대신 검증한 동적 함대 문맥을 전달한다. 저장된 출격 당시 함종/모듈/출발지로 보고서의 결정론 검증을 수행한다. 임의 함선 ID·타 참가자 함선·이동 중 함선·중복 ID는 거절한다.
- 새 함선으로 개인 임무 출격/귀환과 공동 역할 수행을 각각 검증한다. 새 재고를 조선소 카운터에만 표시한 상태는 완료가 아니다.

## 서버 명령과 작업 시각

기존 루프백 서버·개발 참가자 세션·출처 검사·본문 한도를 재사용한다. 실제 계정 인증이나 원격 서비스는 이번 범위가 아니다.

- 제국 조회는 인증 세션의 개인 상태와 serverTime을 반환한다. `/api/empire`와 `/api/empire/commands`를 추가한다.
- 새 명령은 `{ commandId, expectedEmpireRevision, action }`을 사용한다. 각 시작/취소/정비/출격 명령에는 필요한 행성 ID·작업 ID·함선 ID가 들어간다. 공동 operationId는 개인 제국 명령의 선행 조건이 아니다.
- 클라이언트는 비용·작업 시간·수준·지급 재고·완료 판정을 전송하지 않는다. 서버가 콘텐츠와 현재 자산으로 계산한다.
- 같은 SQLite에 제국 영수증을 별도 namespace/table로 저장한다. 기존 공동 영수증의 키·원 요청은 유지한다. 전체 원 요청 지문을 비교하고 같은 ID의 다른 내용은409로 거절한다.
- 실행 트랜잭션은 영수증 조회 → 기존 확정 상태 검증 → 예상 revision 검사 → serverTime까지 생산/작업 정산 → 새 명령 적용 → 저장/영수증 작성이다. duplicate는 원 실행을 다시 적용하지 않는다.
- 개인 revision은 개인 명령 성공 시 증가한다. 공동 역할이 개인 자산을 바꾸면 해당 개인 revision도 증가한다. 다른 참가자의 공동 역할이나 공동 작전 교체만으로 개인 명령을 거절하지 않는다.
- 조회는 serverTime까지의 순수 투영을 반환한다. 조회 자체가 작업을 반복 지급하거나 revision을 증가시키지 않는다. 다음 명령에서 동일한 투영을 장부에 확정한다. 완료 시 생성 함선 ID는 작업 ID와 인덱스로 결정해 반복 투영도 같은 결과다.
- 같은 완료 시각은 작업 ID 순서로 안정적으로 처리한다. 작업 효과는 완료 시각에 적용하고 그 뒤 생산에 사용한다. 시계가 뒤로 가면 이미 반영한 성장/완료를 되돌리지 않는다.
- 처리 결과 불명 명령은 메뉴/행성 전환/새로고침 뒤에도 원 행성·원 ID·원 내용을 보존한다. 확인 전 새 명령과 참가자 변경을 막는다. 오래된 duplicate 영수증이 최신 화면을 덮어쓰지 않도록 재전송 뒤 최신 개인 상태를 조회한다.

## v1/v2 저장과 영수증 이전

이전은 시작 시 SQLite 트랜잭션 하나에서 수행한다. 중간 실패 시 world와 모든 영수증이 함께 되돌아간다. 알 수 없는 버전/손상된 자료를 초기화하지 않는다.

1. v1은 기존 검증과 v1→v2 이전 경로를 거친 뒤 v3로 이전한다. v2는 기존 검증을 통과한 원자료에서 시작한다.
2. 참가자별 본성 ID를 참가자 ID에서 결정한다. 기존 합금은 합금, 보급은 연료로 같은 수량을 옮긴다. 새 결정 자원80과 결정 시설1·발전소1·조선소1·연구소1은 한 번만 지급한다.
3. 기존 forge 수준은 합금 광산, reactor 수준은 연료 합성소 수준으로 옮긴다. 해당 자원의 기존 저장 상한과 생산률을 유지한다. 기존 생산 기준 시각/보정량은 같은 계산 단위로 보존한다. 새 결정의 생산 시각은 이전 시각부터 시작하므로 과거 접속 공백 생산을 소급 지급하지 않는다.
4. 기존9척의 ID·함종·정비량을 본성의 실제 함선으로 옮긴다. 진행 중 개인 작전의 함선은 출격 상태, 원점은 본성으로 지정한다. result 상태의 반환 함선과 정산된 화물을 다시 지급하지 않는다.
5. 연구 데이터·임무별 최고 성과·해금 모듈·활성 모듈·출격 횟수·진행 작전·다음 작전 ID·공동 예약/보고서/공헌/보상은 보존한다. 새 기술은0에서 시작한다.
6. 기존 공동 영수증의 원 요청 지문과 receipt 식별자는 바꾸지 않는다. 영수증 응답은 그 영수증 상태를 검증하고 같은 순수 이전 규칙으로 변환한다. 응답 변환은 보관 상태의 형식 변환이며 현재 world에 보상이나 자산을 재적용하는 것이 아니다.
7. 이전 뒤 원 pending 명령의 duplicate를 반환할 수 있어야 한다. 이전되지 않은 새 구형 기지 명령은 원래 지정이 없으므로 본성 대상으로 해석한다. 구형 명령은 기존 revision 계약을 유지하고, 새 대시보드는 새 개인 명령을 사용한다.
8. 두 번째 서버 시작에는 초기 결정/시설/함선을 다시 추가하거나 생산 시각을 초기화하지 않는다. browser practice 저장은 자동 이전하지 않는다.

## v0.5 화면 구현

기본 진입 화면을 행성 대시보드로 바꾸고 브라우저 연습·기존 작전으로 실제 탐색할 수 있게 한다. 화면의 왼쪽 탐색, 상단 현지 자원, 중앙 행성과 시설, 우측 행동, 하단 진행 목록을 v0.5 배치로 연결한다.

- 상단: 선택 행성 이름, 자원/상한, 현재 분당 생산, 전력 수요/공급과 부족량. 제국 총자원을 현지 가용 비용으로 사용하지 않는다.
- 중앙: 실제 소유 행성 한 곳의 선택기, 노바 프라임, 시설 공간, 실제 소유 행성 수. 생산 시설·조선소·방어 거점은 키보드로 선택 가능한 버튼이다. 선택 마커와 우측 제목/비용이 같은 대상을 가리킨다.
- 우측: 생산/발전 시설 증설, 조선 함종·수량·비용·시간·해금 조건, 현지 포대 건설, 공통 연구, 재고/정비 중 선택 항목에 맞는 실제 행동을 표시한다. 숫자 입력에 최소/최대와 서버 부족 사유를 제공한다.
- 하단: 현지 건설·조선과 제국 연구를 구분하고 작업 출처 행성, 대상, 수량, 진행, 남은 시간, 취소 비용을 표시한다. 전체 보기를 누르면 다른 소유 행성의 작업도 이름과 함께 조회한다.
- 함대 보기: 함종별 보유/가용/정비/출격 수량, 실제 함선 선택과 현지 정비를 제공한다. 예정 건조와 가용 재고를 분리한다.
- 새 연구는 별도 탭/패널에서 실제 비용 출처를 선택한다. 기존 모듈과 연구 데이터는 서버 작전의 별도 상세로 표시한다.
- 보고서는 실제 건설·조선·연구 완료/취소와 기존 전투 보고서를 보여준다. 외부 수송/정찰/공격 접근이 없으면 시안의 이벤트를 가짜로 생성하지 않는다.
- 은하계·개척·랭킹·위협 대응은 이번에 실행되지 않는다. 실제 기능처럼 보이는 빈 CTA를 두지 않고 후속 항목은 설명에서만 안내한다. 공격 접근 시안의 상태 전환은 다음 성계 단계다.

### 그림·반응·접근성

v0.5 PNG를 통째로 배경에 놓아 이미 그려진 숫자/버튼 위에 클릭 영역을 씌우지 않는다. 행성/시설 그림은 텍스트 없는 장면 자산으로 분리하고 라벨·마커·HUD·입력은 React/CSS로 구현한다. 넓은 세라믹 면·흑연 구조·구리·청록 색 역할을 유지한다. 별도 장면 자산이 필요하면 원본 PNG를 보존한 파생 파일을 사용한다.

선택120~180ms, 패널180~260ms, 완료 사건400~700ms를 기준으로 하되 명령 전송/다음 입력을 막지 않는다. `prefers-reduced-motion`, 키보드 포커스, 색 외 상태 텍스트, 완료 알림을 제공한다. 화면이 좁아지면 HUD → 행성/시설 → 행동 → 진행 목록 순서로 재배치한다. 서버 확인 전에는 예상 생산/남은 시간을 현재 확정 재고와 구별하고 연결 실패 시 마지막 상태와 확인 시각을 유지한다.

## 완료 기준과 검증

1. 본성의 실제 생산 자원으로 시설 증설·연구·함선 건조·포대 건설을 수행하고, 서로 독립된 작업 목록에서 완료를 확인한다.
2. 건조한 함선이 해당 행성의 재고에 한 번 추가되고 개인/공동 작전에 사용되며 귀환/정비 결과가 같은 장부에 남는다.
3. 두 행성 픽스처에서 선택 변경·비용 지불·작업 완료·정비·출격·귀환이 다른 행성 자원을 소비하거나 함선을 복제하지 않는다. 연구 효과만 공통으로 적용된다.
4. 시간 경계·전력 부족·오프라인8시간·저장 포화·완료 직전 취소·환불 상한·동시 시작·중복 명령·서버 재시작·미확정 명령 복구를 행동 중심 테스트로 확인한다.
5. v1/v2 정상 자료/영수증/진행 작전 이전, 재시작 재이전 방지, 손상 영수증과 SQL 오류의 전체 롤백을 검사한다.
6. 행성 화면은 실제 데이터/명령으로 작동하고 시안의 가짜 수치/행성/작업을 표시하지 않는다. 키보드 선택·입력 검증·부족 사유·모션 감소와 협소 화면 스타일을 헤드리스로 검사한다.
7. 기존 `npm test`, `npm run build`, `npm run verify:build`, `npm run verify:guild`, `npm run simulate`와 신규 제국 HTTP/저장 통합 검증을 통과한다. 임시 DB를 사용하며 사용자의 실제 DB를 테스트용으로 초기화하지 않는다.
8. 검증은 헤드리스로만 수행한다. 새 창·브라우저·편집기·렌더러를 열지 않는다. 실제 화면 품질·터치·모션 체감·재미는 별도 플레이 검증 상태로 보고한다.
