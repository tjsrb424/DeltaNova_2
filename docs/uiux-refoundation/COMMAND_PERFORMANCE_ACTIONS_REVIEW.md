# 명령 성능 원인 분리·주요 행동 우선 배치

2026-10-16 · `codex/demo-visual-unification` · 이번 비교 기준 `255fa766ee92e1c1794e440e9e35d02c5b1ea080`

독립 데모에서 명령 화면의 로딩·입력 경로를 계측하고, 주요 조작을 설명보다 먼저 배치했다. 데이터 연결, 실제 서비스 UI 이관, 게임 모델/산식, 의존성은 변경하지 않았다. 기존255fa의 느린 표본은 [이전 원문](../qa/2026-10-16-mobile-a11y-loading/performance.json)에 보존한다. [최신 검증 원문·캡처](../qa/2026-10-16-command-performance-actions/README.md), [다른 PC에서 이어가기](./HANDOFF.md).

## 원인 분리와 변경

1. **초기화 중복:** 직접 명령 진입도 홈을 배치한 뒤 선택한 화면을 다시 배치했다. 공통 snapshot 표시 뒤 내비게이션이 선택한 화면을 한 번 생성하도록 했다. 숨겨진 행성의 항로 측정은 건너뛰되 표시 시의 기존 측정·항로 시계는 유지한다.
2. **입력 중 레이아웃 강제 확정:** 수량마다 요약3영역을 교체하고 focus/style/scroll를 다시 확인한 뒤 animation 재시작을 위해 offsetWidth를 읽었다. 표시 전용 영역의 바뀐 text/attribute만 패치해 노드를 보존하고, 입력 포커스/스크롤을 불필요하게 다시 설정하지 않는다. lift 모션은 두 CSS animation 이름을 교대로 사용해 동기 레이아웃 읽기 없이 재시작한다. 공유한 편성 요약으로 표시를 갱신한다.
3. **이미 처리한 값의 중복 확정:** input 뒤 같은 값의 change가 오면 표시/안내를 다시 만들었다. 이미 반영한 같은 값은 다시 처리하지 않는다. 비어 있거나 실제로 바뀐 change-only 입력은 기존 정규화/검증 경로로 처리한다.
4. **모듈 요청 연결:** 마지막 단계에서 발견되는 공통 모듈3개를 CSS 링크 뒤에서 modulepreload한다. 새 파일·라이브러리·캐시·가짜 준비 상태를 추가하지 않는다. 힌트3개만 응답 HTML에서 제거한 대조군을 별도로 계측한다.

30회 입력/로드의 비용 모드와, 제품 파일을 바꾸지 않은 cold-load 모드를 분리했다. 비용 모드의 함수 wrapper는 검수 서버가 보내는 main.js에만 있으며 런타임 제품 코드에 계측용 API를 만들지 않았다. 서버 파일 읽기(Server-Timing), 브라우저 요청 대기/수신(Resource Timing), 함수 비용, DevTools의 style/layout 횟수·시간을 함께 기록했다. 사용자 PC의 과거 이상치 원인을 소급해 확정할 수는 없다. 현재 반복 재현되는 낭비와 관측 변동을 구분한다.

5. **격납고 배경 발견 지연:** 추가 계측에서 같은 격납고가 LCP 후보였고, CSS 배치 뒤에 이미지 요청이 시작됐다. 직접 명령 진입에서만 이미 쓰는 격납고를 낮은 우선순위로 선로딩한다. 건설 직접 진입에서는 이 이미지를 요청하지 않고 명령에서는1회만 요청하는지 확인한다. 아트 파일/품질을 바꿔 수치를 줄이지 않는다.

## 실행과 설명의 순서

- 건설: 시설 선택 → 선택 시설명/수준·실행 영역 → 현재 건설 → 아트·효과·전체 비용·조건·설명. 시설을 바꿔도 현재 건설 표시를 유지한다. 실행 버튼은 계속 **미연결/비활성**이다.
- 연구: 연구소 비교를 상단 주 행동으로 두고 안내를 아래에 둔다. 연구 시작 미연결 버튼과 현지 자원 확인도 각 카드의 위에 둔다.
- 함대: 함대 보내기 진입을 설명·시연 함대 목록보다 먼저 두고, 다음 조선소/편성 실험실 조작을 투자 설명 위에 둔다.
- 명령: 명령 확인 버튼을 요약 상단에 둔다. 수량/지휘 오류의 표시와 disabled 조건은 그대로다. 확인 단계에서 정확한 편성/비용을 보고 출항 시연을 직접 선택하는 흐름을 유지한다.
- 홈: 결정 카드의 주 행동을 제목 다음, 설명·진행 표시 전에 둔다.

320px에서 수준 배지가 별도 줄로 밀리면서 실행 버튼이 하단 메뉴에 닿는 문제도 수정했다. 이름과 수준을 함께 묶고 여백을 조정한다. 원래 비용·조건·대기열·도움말과 조작은 모두 보존한다. 키보드/화면 읽기 순서도 버튼→설명으로 일치시켰다.


## 측정 해석

파일 서버의 요청당 파일 읽기에서 최대1366.7ms가 관측됐다. RAM에 양쪽 파일을 측정 전에 올린 대조군에서는 이 대기가 거의 없어졌지만 브라우저/공유 호스트의 시간 변동은 계속 있었다. 파일 I/O만을 모든 악화의 원인으로 확정하지 않는다. 첫 RAM8쌍에서도 load/LCP·입력 doubleRAF p95가 악화돼 원문을 보존했고, 그 기록으로 CSS 격납고 요청 시작 시점을 추적해 선로딩을 보완했다. 동일 후보 이미지/크기도 기록한다.

최종은 제품 파일을 바꾸지 않은 파일 서버8쌍과 별도 RAM 서버8쌍을 분리한다. 각 로드6회의 합성 수량 변경과 doubleRAF, 동기 이벤트 처리, 서버/리소스 타이밍을 함께 보존한다. 양쪽 모두390×844/DPR3·down1.6Mbps/up750kbps·설정latency150ms·CPU4배·브라우저 cache off·전후 교차이다. RAM은 서버 조건을 바꾼 별도 실험이며 원래 파일 서버 측정을 대체하지 않는다. 과거18회에서 nearest-rank p95는 최대값에 해당했다. 이번48회 p95도 실제 기기 INP/사용자 모집단 통계로 표현하지 않는다.

최종 각 모드는8쌍/16 cold loads, 양쪽 각각48개 합성 입력이다. 모든 표본을 남겼다. 파일 서버의 LCP는21.2%, load는7.4%, 입력 동기 처리 중앙값은72.8%, doubleRAF p95는35.9% 감소했다. RAM 서버에서도 같은 방향이었다. 입력당 layout은 양쪽 모드의 모든 로드에서3회→1회(6입력당18→6)였다. 양쪽 모두 같은 격납고 이미지·44982px 후보를 기록했고 파일 내용과 프레임 크기를 낮추지 않았다.

**비용도 남아 있다.** DOM 초기화는 파일 서버203.25ms/RAM199.65ms 늘었다. FCP도38ms/24ms 늘었다. 격납고를 더 일찍 요청하며 대역폭을 나눠 쓰는 비용과 화면 표시 이점을 함께 보고 채택했다. JS/HTML/CSS 본문 합계는700,058→702,465bytes(+2,407bytes,약0.34%)였다. 명령의 격납고 요청은1회이며 건설에서는 추가 요청0이다.

파일 서버 DOM 초기화의 최종 범위는 전3080.20~3416.40ms / 후3446.80~3689.30ms, RAM은 전2947.10~3577.30ms / 후3318.10~3977.60ms였다. 과거14~30초 표본까지 모두 해결됐다는 뜻은 아니다. 원본 파일 서버 진단, 초기 RAM 실험의 악화, 선로딩 보완 뒤 두 최종 모드를 구분한다. [최소/최대·정의·후보](../qa/2026-10-16-command-performance-actions/performance-analysis.json).


## 최종 검증과 평가

- 최종 제품 파일에서 전체 **32파일·329테스트 통과**, build/verify:build 성공.
- 최종 dist의 행동 우선 검사 **7/7**, 모바일/접근성 **11/11**, 기존 통합 **35개/15레이아웃** 통과.
- 전체15화면 검수 **11개/일반120개·글자200%45개 레이아웃** 통과.
- 자유 편성 **14개/8레이아웃** 통과. 모든 함종 직접 수량 조절, 같은 편성 확인/뒤로가기, 가용량·지휘 제한, 모션 줄이기와 그림 누락 대체 표시를 유지한다.
- headless 캡처에서 건설320/390, 연구390, 명령 요약390, 글자200%를 직접 검토했다. 320px 실행 버튼은 하단 내비게이션과12px 이상 떨어지며 설명·전체 비용/조건·현재 건설을 보존한다. 200%에서는 스크롤이 필요하며 키보드로 버튼에 접근할 수 있다.
- 기존 통합 검수의 h3 선택자가 현재 건설 제목과 충돌한 실패도 보존했다. 제품에서 대기열을 없애지 않고 검사에서 시설 제목을 구체적으로 선택했다.
- 마지막 읽기 코드 검토에서 버그/범위 회귀를 발견하지 못했다. 코드 검토는 실행 검수를 대체하지 않는다.

UX 판단은 주 행동의 위치·도달성, 정확한 편성 피드백, 비용/조건 보존을 기준으로 했다. 함대 그래픽은 [이전 V2 내부 평가9.60~9.70](../art-source/fleet-refinement-v2/review-gate.json) 후보를 유지하고 로드/크기/해시를 다시 검사했다. 이번에 새 그래픽이나 새 점수를 만들지 않았다. 성능은 최종 표의 조건부 개선이며 DOM 초기화 비용과 공유 호스트 변동, 실제 기기 검수를 남긴다.
